# Decisions

Single source of truth for architecture and process decisions. If another planning document contradicts this file, this file wins.

| Area | Decision | Reason |
|---|---|---|
| Auth | DHBW email verified by a 6-digit code, then a password. Course join code required at registration. **Passkeys are dropped** (operator decision): login stays email and password, with email-code reset. | Email proves DHBW membership; the course code places the user in a course; one login path keeps the app small. |
| Registration | Email + username + course code -> emailed code -> set password. One course per user in the MVP. | Simplest flow that gates on both domain and course. |
| Username | Required at registration, 3–20 letters, digits, `.`, `_` or `-`, unique ignoring case. Shown in the app instead of the email; admins see both. Can be changed later. Accounts from before usernames existed choose one right after login. | Users do not want their email shown everywhere; case-insensitive uniqueness prevents look-alike names such as `Felix` and `felix`. |
| Login | Email + password. | Conventional model users expect. |
| Password reset | Email code, then a new password. Revokes all sessions of that user. Replaces the former recovery code. | Email is the recovery path, so no recovery-code slice. |
| Email storage | Plaintext `users.email`, unique, lowercased. | Needed to send mail on our own initiative. The privacy screen must state that the operator can link an email to a vote. |
| Email domains | Env var `ALLOWED_EMAIL_DOMAINS`, exact domain match, checked before any mail is sent. | Proves DHBW membership and limits spam abuse. Exact campus domains are set in the deploy config. |
| Email sending | Transactional provider (e.g. Resend or Brevo) with SPF, DKIM, DMARC on `felixkarg.de`, behind a single `sendMail` function. | Home-server mail is not deliverable to university addresses. Swappable provider. |
| Email types | Transactional only in the MVP: verification code, reset code. Notifications with opt-in and unsubscribe are post-MVP. | No consent or queue work before shipping. |
| Password | Argon2id, minimum 10 characters, no composition rules. | Current best practice, KISS. |
| Email code | 6 digits from a CSPRNG, stored hashed, valid 10 minutes, single-use, 5 wrong attempts invalidate it, one new code per address per 60 seconds. | Bounded brute-force and resend abuse. |
| Rate limits | Send-code: 5 per IP per hour, 1 per address per 60 s and at most 5 mails per address per hour (over the limit the answer is unchanged and no mail is sent). Login: 5 failures per email, then a growing delay of up to 15 minutes (no permanent lockout), plus at most 20 failed logins per IP per 15 minutes against password spraying. Admin setup code: 5 tries per IP per hour. Email codes: 5 wrong guesses invalidate a code. Username changes: 10 per user per day. Votes: see "Vote cooldown". Live streams: 5 per user. Invite link look-ups: 20 unknown codes per IP per 15 minutes (valid links never count, so a class on one campus network is not limited). Argon2 runs at most 2 hashes at once, so a login flood cannot exhaust memory (64 MiB each). Counters live in memory and reset on restart; Cloudflare in front absorbs floods. | Prevents spam, brute force and resource exhaustion without letting an attacker lock out a victim. |
| Anti-enumeration | Login and reset return the same generic response whether or not the email exists. | Does not leak who is registered. |
| Vote link | `votes(user_id, module_id, vote_value, updated_at)`, composite PK `(user_id, module_id)`, changed via upsert. Users vote only on modules of their own course (others answer 404); clicking the current vote again withdraws it. Deleting a module or user deletes its votes. | KISS. Votes are linked to `user_id`, and `users` holds the email, so votes are not anonymous towards the operator. |
| Live updates | Server-sent events on `GET /api/events` (logged-in users, one stream per open tab, at most 5 per user). A vote change pushes `module-votes` with the module's new totals to everyone in that course; adding or deleting a module (and moving a user out of a course) pushes `modules-changed`. Events carry totals only, never who voted. The overview updates bars in place; the detail page reloads its history. After a reconnect the page reloads to catch missed events. The hub is in memory (one backend instance); a 25 s keep-alive stays under the proxies' idle timeouts and `X-Accel-Buffering: no` stops nginx from buffering. | Everyone looking at a module sees opinions change as they happen, without polling. SSE is one-way and plain HTTP, so it passes nginx, Traefik and Cloudflare without WebSocket setup. |
| Vote cooldown | A user can change or withdraw their vote on a module at most once every 15 minutes (`VOTE_COOLDOWN_MINUTES`), per module; the first vote is always allowed and repeating the current vote is a no-op. Enforced in the backend from `votes.updated_at` (429 `vote_cooldown` with `retryAt`); a withdrawn vote keeps its row with a null value so withdraw-then-vote cannot skip it. Admins are exempt, both for their own votes and for admin actions such as moving a user between courses; their changes still go into the history. The UI locks the buttons and says when voting is possible again. | Keeps the history meaningful and stops scripts from flipping votes, without the counters resetting on a restart. |
| Vote history | Every vote change is appended to `vote_changes(module_id, from_value, to_value, changed_at)` in the same transaction as the vote itself, **without a user id**. The module detail view replays it into the counts at the end of each day (Europe/Berlin) and shows them as a line chart with tooltip and table view. Moving a user to another course withdraws their votes on the old course's modules. | Users want to see how opinions change over time. Without a user id the history cannot be linked to a person and survives account deletion. |
| Vote values | Enum `free` / `possible` / `impossible` (UI: green `#15803d` / amber `#e0a100` / red `#dc2626`, checked with a color-vision validator; every bar carries text labels and counts so it never relies on color alone). | Matches the app's purpose; a single enum column. |
| Session | Server-side session stored in Postgres, opaque ID in an `HttpOnly; Secure; SameSite=Lax` cookie. | Not readable by XSS, revocable server-side. |
| Account deletion | Users delete their own account on `/account` with their password (wrong passwords count towards the login throttle). Their votes are first withdrawn through the normal vote path, so the anonymous history records the removal and totals and graphs stay consistent; then `ON DELETE CASCADE` removes sessions, course membership and votes. The anonymous `vote_changes` stay. The last admin cannot delete their account (409 `last_admin`) and has to promote someone first. | GDPR right to erasure without operator work; history and totals never disagree; the app never ends up without an admin. |
| Data retention | Expired email codes and sessions are deleted hourly (and at backend start), not only rejected. Codes live at most 10 minutes, sessions 30 days. | Data is not kept longer than the privacy page states. |
| Privacy page | `/privacy`, public and in English, linked in the footer of every page and on the registration form. States the controller and contact (`mail@felixkarg.de`), every stored item with purpose and retention, that the operator can link votes to emails, Cloudflare and Resend as processors, the legal basis and GDPR rights. Its table must be updated whenever the stored data changes. | Required by the GDPR and by the email-storage decision above; one place that matches what the code actually does. |
| security.txt | `frontend/public/.well-known/security.txt`, mirroring `felixkarg.de`: contact, PGP keys, languages; `Canonical` points to `free.felixkarg.de`. `Expires` is 2027-05-01 and has to be renewed before then. | Standard way (RFC 9116) for security researchers to report problems. |
| Activity and access logs | Two logs in the `audit_log` table, readable only by admins on `/admin/activity`. The **activity log** records what admins change (courses, modules, roles, course moves, join codes) and is kept 1 year; the **access log** records registrations, logins, failed logins, password resets, joining or switching a course and deleted accounts, and is kept 90 days. Each entry has the time, the user (names resolved live), the **full email address** and the **full IP address** of the request, as the operator decided (an earlier plan to shorten addresses and leave emails out was dropped). A failed login records the address that was typed even if no account has it, and a reset request for an unknown address is recorded too. Only attempts that got past the rate limits are written, so the log cannot be flooded. Both logs can be filtered on the server so they cover the whole log: a search over email, IP address, names and the subject (course, module), a filter for the kind of event, and a time range (24 hours, 7 days, 30 days); clicking an email or IP in a row searches for it. Recording is best effort and never stops an action. Entries expire only by retention time: when an account is deleted its user link goes, but the email and address stay until expiry. The privacy page lists both logs and says so. | Admins need to see who did what and from where to investigate abuse and mistakes. Full emails and addresses are the operator's explicit choice; short retention times and the privacy page keep it proportionate. |
| Backups | Each instance runs a `backup` service (same Postgres image) that dumps the database at start and then daily, restores every dump into a scratch database and compares row counts to prove it is usable, keeps 30 days (older than two days: one per day) and reports its health to Docker. Files go to `BACKUP_DIR` (a host directory) or a Docker volume. Restoring is a documented, scripted procedure (`deploy/backup/restore.sh`: `check` is safe, `apply` needs a confirmation and saves the current state first). The scripts are tested in CI. An off-site, encrypted copy is the operator's job (`docs/backups.md`). The privacy page lists backups: a copy of all data for up to 30 days, so deleted data can remain in a backup that long. | A database that only exists once is one mistake from gone. Verifying by restoring is the only proof a backup works. Keeping it as a service means it deploys with the app and needs no host setup. |
| Languages | The interface is available in English and German. The language is stored on the account (`users.language`, default English), so it follows the user to every device and is changed under Account. Visitors who are not logged in get their browser language (German for German browsers, else English), can switch it in the footer, and the choice is kept in the browser's local storage; after logging in the account language wins, and after logging out the page keeps it. Code mails for registration and password reset are written in the language the visitor reads the page in (for a reset without one, the account's). Texts live in typed catalogs (`frontend/src/i18n/en.ts` is the source of truth, `de.ts` must have the same keys, which the compiler checks); API errors are codes that the client translates. German is informal ("du") and calls the three votes "Geschenkt", "Machbar" and "Unmöglich". The privacy page and `security.txt` stay English only. | Students are German, but English was the project language; storing the choice on the account makes it permanent and lets emails match. A typed catalog makes a missing translation a build error. |
| Product name | The product is written FreeSite in the interface, emails, manifest and docs, in both languages. Repository, database, Docker and domain names keep their technical spelling (`free_site`, `free-site`, `free.felixkarg.de`). | One consistent brand; technical names are not user-facing and renaming them would break deployments. |
| PWA and branding | The logo is three rounded bars in the vote colors (a miniature of the vote bar), shown in the header and rendered by `frontend/scripts/build-icons.mjs` into an SVG favicon and PNG app icons (192, 512, maskable, Apple touch). The app is installable (`manifest.webmanifest`, standalone). Non-production instances (`INSTANCE_LABEL`) get their own name, blue theme color and blue icons, so an installed dev app is never mistaken for the real one. A minimal service worker (`sw.js`) only provides an offline page: page loads always try the network first, and the API and live updates are never intercepted or cached, so deploys are never hidden behind a stale copy and no personal data lands in a cache. nginx serves `sw.js` and the manifest with `Cache-Control: no-cache`. | Students open the app on their phones; installing it puts it on the home screen. Scoping the worker to an offline page gives that without the staleness and privacy risks of caching the app or its data. |
| Invite links | Every course's invite link is `https://<site>/join/<join code>`: it reuses the join code, so rotating the code revokes the link and nothing extra is stored. Guests see the course name and continue to registration (course prefilled, no code field) or login (which continues at the link). A logged-in user without a course joins in one click; one in another course must confirm the switch, which withdraws their votes in the old course (same as when an admin moves them); one already in the course is told so. Look-ups are public and show the course name only. `Referrer-Policy: no-referrer` keeps the code out of referrers. Admins copy the link from the course list. | Onboarding a class becomes one shared link instead of a code to type. Reusing the join code keeps one secret per course and one place to revoke it. |
| Voting deadline | Each module has an optional `modules.voting_ends_at`. From that time on the verdict is frozen: setting, changing or withdrawing a vote is refused with `voting_closed` (409), for admins too, and the overview marks the module as final. Admins set the deadline per module (empty = open, clearing it reopens voting) or press "End voting for semester N" on a course, which sets the deadline to now for the semester's still-open modules. Both are recorded in the activity log as module changes. | The verdict of a past exam should not change any more, and a semester-wide button is the common case at the end of a semester. Grades (next step) build on this date. |
| Grades | After voting on a module has ended, every member of the course may enter their own grade, 1.0 to 5.0 in steps of 0.1 (`grades(user_id, module_id, grade_tenths, updated_at)`, one per user and module, change or remove at any time; `voting_open` 409 before the deadline). Grades are linked to the account like votes and deleted with it (`ON DELETE CASCADE`). Others never see single grades: the API returns only the user's own grade plus average, best and worst grade of the module, and only from `MIN_GRADES_SHOWN` = 5 grades on. Modules with ended voting move to a collapsed "Past modules" list on the home page. The privacy page lists grades. | Grades are sensitive and class sizes are small, so only an aggregate over several people is shown; the threshold keeps single grades from being guessed. Entering them only after the verdict is frozen keeps them from influencing votes. |
| Course management | Admins are global: every admin manages all courses, modules, join codes and users. Admins create and delete courses and modules, rotate join codes, and move a user to another course or remove them from their course. A course can only be deleted when it has no members; its modules go with it. Admins can also rename a course (its join code is kept, so shared links keep working) and rename a module or move it to another semester (votes and history stay). The admin screen shows a summary (courses, users, admins, users without a course), one card per course with a "Copy invite link" button (the link itself is not displayed) and an inline module list (several can be open at once), and a searchable user table filtered by course and role, 20 rows at a time. | Deleting an empty course cannot remove accounts by accident. Global admins fit a small app run by a few trusted people. |
| Admin | `ADMIN_SETUP_CODE` env var used at registration creates the first admin; it is accepted only while no admin exists. `users.role` is `user` or `admin`. Admins can promote and demote others, never themselves. | The code cannot mint a second admin even if it leaks, so rotating it is optional. The admin's email must still pass the domain check, and a course code is still required. |
| Backend | Node.js, TypeScript, Express, Drizzle ORM, PostgreSQL. | Typed parameterized queries; readable SQL migrations. |
| Frontend | Vite, React, TypeScript, React Router, plain mobile-first CSS. | Small app (4 screens); matches `DevelopingRules.md`. Screens are designed fresh later; the old Stitch prototype is discarded. |
| Visual design | Specified in [`DESIGN.md`](../DESIGN.md): color tokens on `:root` with a separate dark mode (follows the system setting), the Geist typeface and Phosphor icons (both self-hosted from npm, no font CDN), one sticky app bar, a verdict per module ("Mostly free 62%"), vote buttons as one joined control. The vote colors are validated for color-vision deficiencies in both modes; text never relies on them. | One written source for how screens look, so new screens stay consistent; self-hosting keeps the privacy page true (no third-party requests). |
| Repo | npm workspaces monorepo: `frontend/`, `backend/`, `shared/`, plus `docker-compose.yml`. Each package has its own Dockerfile. | One PR flow and CI; shared API types and vote enum avoid drift. |
| Testing | Vitest everywhere, Testing Library for React, real-Postgres integration tests, mail sending mocked at their boundaries, TDD per slice. Browser-level tests are in the next row. | Upsert and constraint logic is where bugs live. |
| Hosting | Own homeserver, Docker Compose. Production publishes no host ports; an existing Traefik instance and Cloudflare Tunnel (already used for other apps on the same infra) route to it, via a generic `FRONTEND_BIND` address/port. Deploys run on a shared GitHub Actions self-hosted runner (no dedicated one). | Reuses infra that already exists instead of standing up a second tunnel or runner; see `docs/deployment.md` (kept generic, since the repo is public). |
| Domain | `free.felixkarg.de`, The dev instance runs on `free-dev.felixkarg.de` (one level, so Cloudflare's free `*.felixkarg.de` certificate covers it). | Links, the PWA install and the cookie are bound to the domain, so it should not change once users register. |
| Git | `main` = production, `develop` = integration, `feature/*` branches. Merging into `develop` deploys the dev instance (`free-dev.felixkarg.de`, own compose project and database); merging `develop` into `main` deploys production. | Follows `DevelopingRules.md`; every change is tried on a production-like instance before it reaches users. |

## Build order

1. ✅ Walking skeleton: monorepo scaffold, Docker Compose (frontend, backend, Postgres), `/api/health` endpoint, CI (lint, test, build), first deployment to `free.felixkarg.de` via the existing reverse proxy.
2. ✅ Registration and login: email code, password, course code, sessions, password reset, `sendMail` with the provider configured (DNS records included).
3. ✅ Admin bootstrap (`ADMIN_SETUP_CODE`, `/claim-admin`); create courses, join codes and modules on `/admin`.
4. ✅ Voting (upsert) and overview with bar chart: the home screen lists the modules of the user's course by semester, each with a stacked bar of the vote shares and three vote buttons.
5. ✅ Detail view (`/modules/:id`: current shares, vote buttons, history graph over time) and privacy info screen (`/privacy`, public, in English), plus self-service account deletion and `/.well-known/security.txt`.
6. ✅ Invite links (`/join/<code>`), admin redesign with the optional module management, header with logo, favicon and PWA, English and German per account.
7. ✅ Database backups with a tested restore, end-to-end tests in CI, activity and access logs with search and filters.
8. Semester rollover: voting deadline per module, then optional grades with an average once enough are in.
9. Release `develop` to `main` once the semester rollover is implemented and running on the dev instance (operator go-ahead given for that release).

Passkeys and "My devices" were dropped from the plan.

## Post-MVP

Comments, profile settings, "my modules" list, email notifications with opt-in and unsubscribe, joining several courses.
